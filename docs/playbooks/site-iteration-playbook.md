# 运维手册：对外网站迭代（合规白标 · 真实验证发布 · 漏斗一致性）

> 来源：website-workflow 仓（2026-10-31 立，2026-11-08 并入本仓，见 decisions/2026-11-08-website-workflow-merge.md）。
> 适用：营销主站、课程站、演示站等对外站点的内容迭代、视觉改版、合规审查、发布与验证。
> 不适用：产品工程（走内部 loong-workflow 本体）。

## 一、合规红线（白标）——先于一切

**任何对外内容（页面文字、截图、PDF、课件封面、og meta），永不出现真实客户名与上游厂商痕迹。**（黑名单清单维护在各站内部规则文件，含客户名与竞品厂商名两类；本仓公开版不列具体词条。）

1. **数值可以留，名称必须走**：客户规模、行业类别、效果数字保留——承载专业感；可识别名称一律剥离。
2. **截图是重灾区**：新截图必须过 OCR 识别文本比黑名单；图源文件先修图（渐变填充抹品牌框）再上站。
3. **蹭方法论不蹭品牌**：可采用上游框架，但引擎名/公司名/产品型号必须替换为本站白标语言。
4. **新内容入场即自查**：新增文案块对黑名单 grep 一次再提交。
5. **泄露处置**：发现已上线命中→立即修复并 push；截图类重制替换；事件记入 retrospectives/。

## 二、真实验证发布（Verify Before Live）

**宣布「已上线」前四步缺一不可：**

1. **本地双端渲染**：headless 浏览器（`--no-sandbox`）1440×900 桌面 + 390×844 移动各一遍：零破图、零横向溢出、零 pageerror、敏感词零命中、目标板块存在。
2. **链接独立复验**：新增外链/下载链逐条 `curl -r 0-255 -L` 打 200——**不依赖测试脚本内置路径模式**（模式会过时，坏链检查会误报新链接）。
3. **真实 push 成功**：push 后 `git log origin/main -1` 确认远端 SHA 等于本地；443 超时是常态，退避重试（20→45→60s），连续三次失败再换通道。
4. **live 回读**：等部署窗口（Pages ~55s）后带 cache-bust 参数拉回线上 HTML，grep 本次新增特征字符串命中才算上线成立。
5. **内容页标题溯源数据源**：页面 h1/卡片标题必须读自数据文件，禁止在页面内硬编码主题串；对账=标题串在数据文件中 grep 命中 ≥1。实测事故：页面硬编码了另一业务线的主题，仓内正确数据文件存在却未被消费，HTTP 200 但内容全错。
6. **SPA 页面断言按页给特征词**：每页至少 1 个关键词；某页 DOM 体积显著小于同站其他页（壳级）即判未渲染或渲染错主题。

辅助纪律：结构变更跑 html.parser 标签配对（双栏卡片最易漏闭合）；CSS 改动数 `{}` 配平；reveal 动画新卡片类追加进 main.js 选择器；本地测试 http.server 用毕 kill（避免测试跑在旧内容上）。

## 三、漏斗一致性（Funnel Consistency)

**任何新板块/新文案/新产品位，动手前先回答：它落在漏斗哪一环？** 回答不出来→不做；同环已有载体→并入不新增。

1. **一环一载体**：合作路径只讲一条，不许两个板块各讲一遍；新想法先找旧载体，改旧优于建新。
2. **命名过业务语**：对外文案禁内部黑话（工程术语/机制名）；检查法=把标题念给目标客户听，复述不出来就重写。标题改动同步 `<title>`/meta description/og:* 三件套。
3. **CTA 双轨制**：企业客户与行业伙伴永远两个独立入口，mailto 用 `?subject=` 区分来源。
4. **定期扫旧**：每次新增板块后通读整页 nav 与 section 顺序，删与旧载体重复的内容；关键词堆叠、无名列表优先清除。

## 四、发布前检查清单（按序全过才 push）

**内容合规**：黑名单 grep 零命中；新截图过 OCR；无内部黑话入对外文案。

**结构**：标签配对栈空；CSS 配平；新卡片类进 reveal 选择器；nav 锚点与 section id 一一对应；workflow 引用的脚本在树内存在（删脚本须同批改 workflow）；内容页标题串在数据文件中命中 ≥1（不硬编码主题）。

**漏斗**：新内容答得出漏斗归属；CTA 双轨 subject 区分；title/meta/og 同步。

**验证**：双端渲染四零；新增链接逐条 200；push 后 SHA 对账；live 回读特征串命中。

**提交卫生**：commit message 无凭据值；测试进程已 kill。

## 五、宣传改写方法论（内部视角→买方语言，2026-11-04 实证）

| 翻译规则 | 例 |
|---|---|
| 机制数量不露，机制翻译成承诺 | 「N 条工程铁律」→「做完的每一步都有证据」 |
| 「我们怎么造」改「你得到什么」 | 开发流水线→「干得好的活沉淀成技能，下次一句话复用」 |
| 调度术语过兵法/直白话 | map/pipeline/race→分进合击/流水接力 |

- **能力宣传三档诚实性**：已上线才说有；灰度才说近期；没做不说。
- **最低成本扩版**：新板块优先扫描现有 section 的 DOM 模式做「样式克隆」（零新 CSS=零遗漏风险）；现有类表达不了才新增，新增必同步 reveal 选择器。
- **版本号从机器可读源生成**（latest.yml 类），不手抄——手抄必落后一版才发现。
- **公网回环 000≠链接坏**：出网受限环境 curl 公网 IP 得 000，先打本机回环复验（200 即资源在），公网可达性另行抽测。

## 六、push 失败两类常见形态

1. 443 连接超时：退避重试（verify 铁律第 3 步）。
2. non-fast-forward 被拒：远端有新提交是常态，`git pull --rebase` 重推；先查远端真身再重试。
